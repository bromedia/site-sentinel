# Rules bundles

Sentinel ships with a built-in signature set that works without any download, and `update-rules` can replace it with a newer signed bundle.

## Built-in set

`rules/builtin.json` (about 50 rules) is generated by `rules/generate.php` and compiled into `sentinel.php` by the build. The rules are original to this project and target techniques common in WordPress malware: code or commands run from request data, encoded or escaped payloads, function names hidden by splitting, reversing, ROT13 or escape codes, image files included as PHP, hard-coded backdoor accounts, hidden admin users, known webshell and malware family markers, reverse shells, miners, injected script loaders and spam. `critical` rules are near-certain malware; `warning` rules mean "unusual, have it reviewed".

Each rule may be limited to file types with `"files"`: `php` (all PHP extensions and `.inc`), `js`, `html` or `any` (default).

To change the set: edit `rules/generate.php`, run `php rules/generate.php`, and commit both files (a test fails if they disagree). Every rule needs a sample in `tests/test_signatures.php`, and the set must stay silent on the false-positive corpus: WordPress core, Elementor, Yoast SEO, WooCommerce, Contact Form 7 and commonly bundled libraries, pinned in `tests/corpus-repos.txt` (`sh tests/fetch-corpus.sh DIR && php tests/corpus.php DIR/*/`; CI runs it on every push). Accepted matches in legitimate code are listed with a reason in `tests/corpus-allow.txt`.

Never put the literal name of a malware family into the rules (write `Files[M]an`, not the name): hosting providers scan accounts for such strings and could quarantine Sentinel itself. A test enforces this.

Known limits: names split into three or more pieces, novel obfuscation and premium plugins (which are not in the corpus) are not covered; there is no file-hash database yet. Change detection and official checksums remain the backstop.

## Format

`rules.json`:

```json
{
    "version": 12,
    "patterns": [
        { "id": "eval-decoder", "severity": "critical", "regex": "/\\beval\\s*\\(\\s*base64_decode\\s*\\(/i", "description": "eval of an encoded payload", "source": "where this rule came from and its license" }
    ],
    "hashes": [
        { "sha256": "<64 hex characters>", "name": "Malware.Family" }
    ]
}
```

- `severity` is `warning` or `critical`; `regex` is a full PCRE with delimiters and flags. Keep patterns specific; a pattern that matches ordinary code will alert on every deploy.
- `version` must increase with each release. Sentinel refuses a lower version (so an old signed bundle cannot be replayed) and does nothing for an equal one.
- The file is installed byte-for-byte so the signature stays valid.

## Signing and publishing (maintainer)

```
php bin/sign-rules.php keygen                       # once; keep the secret key offline
php bin/sign-rules.php sign rules.json secret.key   # writes rules.json.sig and rules.json.sha256
```

Publish `rules.json`, `rules.json.sig` and `rules.json.sha256` side by side (for example as release assets) and give clients:

```json
"rules_url": "https://example.com/path/rules.json",
"rules_public_key": "<the public key printed by keygen>"
```

Clients with the `sodium` extension verify the ed25519 signature. Clients without it must set `"allow_unsigned_rules": true` to use the `.sha256` file instead; that only guards against corruption, not a compromised rules server, and Sentinel says so each time. Run `update-rules` weekly from cron.

## Licensing of rule sources

Sentinel is open source, but every rule you bundle keeps its own license. Before adding rules from another project (Linux Malware Detect signatures, php-malware-finder, Neo23x0 signature-base, and so on), check that its license allows redistribution and commercial use, keep its attribution, and record the origin and license in each rule's `source` field. The built-in rules in `src/Rules.php` are original to this project.
